# Flux v2 — opportunities deferred from v1

The v1 design doc explicitly excludes the items below. Capture ideas here as
they come up; do not implement in v1.

## Authoring ergonomics
- Inline YAML editor in the browser
- Renaming a screen via URL or query param
- Auto-generating screen ids from titles
- Importing screens from one flow into another
- AI-assisted screen generation

## Visualisation
- Live screen preview pane embedded in the graph view
- Click-edge-to-source navigation (jump from a graph edge to the `to:` line)
- "Presenter mode" / fullscreen graph variant
- Server-rendered Mermaid (avoid client-side rendering flash)

## Modelling
- Variant overrides per actor / experiment
- Cross-flow edges (currently a `to:` only resolves inside its flow)
- Permissions / conditional visibility on screens or actions
- Custom (free-form Jinja) archetypes
- Form field types and validation
- Per-screen background tasks, fake data fetchers, scenario state
- A separate `nav_to:` on `MenuItem` so menu entries don't have to piggy-back
  on `Screen.nav_item` for routing

## Sharing
- Single-file HTML export
- Database persistence (intentionally removed in v1)
- Authentication / session state
- Persisting anything to localStorage

## Open questions still pending owner sign-off
- Tabs as nested subgraph nodes vs edge labels on the parent screen — v1
  picks nested.
- Action with neither `to` nor `opens` — v1 renders a plain non-disabled
  button. Could become disabled if "Annuler" muscle memory wins.
- Multi-actor URL convention — v1 keeps `/<flow>/<screen>`; revisit if
  flow ids collide enough to matter.
